    Glossary

    The vocabulary used throughout this documentation and in the code. Where a term differs from bitcoind usage the bitcoind word is given so the reader can map one to the other, but the libbitcoin word is the one that appears in identifiers, configuration and output.

    Chain

    top
    The highest block of a chain. bitcoind says tip. A chain is a stack, so it has a top and a bottom. top candidate, top confirmed.
    candidate chain
    The chain of headers the node currently believes to be strongest, indexed by height. Blocks on it are downloaded, validated and confirmed in order. Held in the candidate index.
    confirmed chain
    The chain of blocks that have been confirmed, indexed by height. This is the chain the node serves to clients. Held in the confirmed index.
    coalesced
    The confirmed chain has caught up to the candidate chain, so the two tops are the same header. Snapshots and the one-time prevout prune wait for this.
    current
    A chain is current when its top is within a configured window of the present time. Block download, transaction pooling and announcements start only when the chain is current.
    strong
    A transaction is strong at a height if it is in a block on the confirmed chain at or below that height. Confirmation checks that every spent output is strong and unspent. The strong_tx index records it.
    organize
    Insert a header or block into the candidate chain, reorganizing the chain if a stronger branch results. The organize chaser is the only component that changes the candidate chain.
    disorganize
    Reorganize away from a block that has failed validation or confirmation.
    regressed
    The candidate chain was reorganized to a branch point below its previous top.
    milestone
    A block hash and height the operator asserts as valid because they have validated to it before. Blocks at or below the milestone are checked for identity only. Recorded in the header at organization and fixed for the life of the store.
    checkpoint
    A block hash and height fixed in the configuration. Branches under the top reached checkpoint are rejected. Blocks under a checkpoint are checked for identity only.
    bypass
    Validation that skips script evaluation because the block is under a milestone or checkpoint.
    headers first
    Sync by organizing headers into the candidate chain and downloading their blocks concurrently. The default. The alternative, blocks first, organizes whole blocks.

    Transactions and outputs

    point
    A transaction hash and an output index. Identifies an output. The key of the ins table.
    output and input
    The two halves of a spend. An output holds a value and an output script. An input holds a point, an input script, a witness and a sequence. bitcoind says vout, vin, scriptPubKey and scriptSig. libbitcoin says output, input, output script, input script.
    prevout
    The output an input spends, resolved from the store. The prevout table caches them for blocks under validation.
    unspent set
    The set of outputs not yet spent by a confirmed transaction. bitcoind says UTXO set. The term appears only inside bitcoind method and field names on the wire.
    spender
    The input that spends a given output.
    pool
    The set of validated unconfirmed transactions. Open only while the chain is current.
    package
    A set of transactions submitted together and accepted or rejected as a whole.
    template
    A candidate block assembled from the pool for mining.

    Node

    chaser
    One stage of the node pipeline, running on its own strand. The ten chasers are header, block, check, validate, confirm, transaction, template, estimate, snapshot and storage.
    chase
    An event on the node's shared notifier. Chasers communicate only through chase events.
    window
    The span of candidate blocks currently being downloaded ahead of validation. Sized from the connection count and capped by maximum_concurrency.
    split
    Direction to a slow channel to return half its download work and stop, so a faster peer can take it.
    suspend and resume
    Stop and restart all peer connections without stopping the node. Used around snapshots, prunes and disk full.
    fault
    An unrecoverable store error. The node suspends and remains running so the operator can act. Disk full is not a fault.

    Network

    net
    The network object. Owns the thread pool, the strand, the hosts pool and the sessions.
    session
    Maintains a set of channels of one kind: manual, seed, inbound, outbound, or one client-server service.
    channel
    One connection, with timers and state. A channel is a proxy plus connection state.
    proxy
    The serialized message pump over a socket. Owns the read loop and the write queue.
    protocol
    One message exchange attached to a channel. Peer protocols are named by the protocol level that introduced them.
    level
    A peer protocol version number, such as 70016.
    hosts
    The pool of peer addresses learned from seeds and peers, saved to a file between runs.
    bind and safe
    A listening endpoint. A bind accepts plain connections. A safe accepts TLS connections.
    strand
    An executor that never runs two of its handlers concurrently. The unit of state ownership across the stack.

    Store

    store
    The set of memory-mapped tables and their lifecycle: create, open, snapshot, prune, restore, reload, close.
    query
    The interface through which the node and server read and write the store.
    table
    A head and a body. The body holds records, append only. The head holds the bucket array or the record count.
    head and body
    The two files of a table. Heads live under heads/. Bodies live at the store root.
    link
    An offset into a table body. A record link counts rows, a slab link counts bytes. Link width is fixed per table by the schema.
    record and slab
    A fixed-width row, and a variable-length byte range, in a body.
    bucket
    One cell of a hash table head, holding the link of the newest element in its chain and a filter over the chain's keys.
    archive, index, cache, optional
    The four table groups. Archive is the primary data. Index and cache derive from it. Optionals exist only if configured at creation.
    snapshot
    A copy of the heads to primary/, rotating the previous copy to secondary/. A store is restored from its snapshot after an unclean shutdown.
    prune
    Reclaim the prevout cache once the chain has coalesced. Also, for a pruned store, the stripping of input scripts and witnesses under bypass.
    flush lock
    A file held while the store is loaded and released by a clean close. Its presence at open means the store may be inconsistent and triggers a restore.
    envelope
    The settings the store was created with, recorded in the store and governing its sizing thereafter.
    load factor
    Expected elements per bucket. Derived from installed RAM at creation and fixed for the life of the store.

    Server

    service
    One client-facing interface on its own binding: admin, native, bitcoind, btcd, electrum, sparrow, esplora, stratum v1, stratum v2 or bitcoind zmq.
    bitcoind
    The original bitcoin node software, and the name of the service that speaks its JSON-RPC and REST interfaces. For consensus behavior the rules are satoshi's.
    native
    libbitcoin's own REST and WebSocket interface and the embedded block explorer.
    admin
    The operator's service: live log and event streams and the embedded console.
