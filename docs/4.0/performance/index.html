    Performance

    This section holds measured behavior of the node and the method behind the measurements. Every number here comes from a recorded run whose source state, configuration and hardware are stated beside it, and every plot is rendered from data published alongside it. Nothing is projected from a partial run.

    Measuring a sync

    Work is proportional to transactions, not blocks. A block at height 100,000 holds a handful of transactions. A block at height 800,000 holds thousands. Half of the transactions in the first 950,000 blocks arrive after height 700,000, and the last 50,000 blocks alone carry twelve percent of them. Progress by height therefore says almost nothing about progress by work, and blocks per minute falls steeply over a sync by design, not by degradation.

    Height Transactions Share
    200,000 7,316,696 0.5%
    400,000 112,477,764 8.3%
    500,000 283,595,037 20.9%
    600,000 466,297,403 34.3%
    700,000 669,566,380 49.2%
    800,000 868,965,224 63.9%
    850,000 1,032,289,555 75.9%
    900,000 1,199,374,722 88.2%
    950,000 1,359,871,695 100%

    Runs are normalized to height 950,000. Comparisons across machines and configurations use wall time to that height, so a run stopped earlier is compared on transactions completed, never on blocks.

    Two modes, two different bottlenecks. A milestone sync does no script evaluation below the milestone, so it is paced by download, identity checks and storage, and is sensitive to network capacity, disk and the operating system's file cache. A full validation sync is paced by script evaluation and by the random reads that resolve each input's previous output against the whole archive. Its working set is the full store, so it degrades monotonically as installed RAM falls below store size and is bound by random read throughput below that point.

    Peers are not a variable. The node manages peer performance aggressively, so a sync from public peers is consistent run to run. Wall time variance between identical runs is under five percent. A larger difference between two runs indicates a protocol difference between them, such as a warm cache from a preceding run, not network conditions.

    A cold baseline requires a reboot. On Windows in particular, pages of a previous store or a previous run remain cached and a repeated run is always faster. Measured runs start from a reboot. Process restart alone is not cold, since mapped pages remain on the standby list.

    What governs memory

    The hash table heads are the resident working set. Their size is the bucket count times the cell width, and bucket count is expected elements divided by load factor. At creation the load factor is derived from installed RAM so that the heads fit the memory available, with the tradeoff that a higher load factor means deeper probes during validation. That cost is paid during initial sync and is noise afterward, since a block every ten minutes does not stress probe depth. The choice is fixed for the life of the store.

    Bodies are append only and are read through the operating system's file cache. Under staging, writes go to anonymous memory and completed rows convert to a read-only file mapping, so no dirty file-backed page exists and the kernel's writeback never competes with the node's own I/O.

    Recorded runs

    Measured sync times by platform, installed RAM, mode and load factor will be published here from archived run artifacts, each with its source shas, configuration and hardware. The plots follow the same rule: data file beside the figure, rendered once, never regenerated from a run in progress.
