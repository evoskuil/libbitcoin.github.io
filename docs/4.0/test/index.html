    Test

    How the stack is tested, at every level from a single method to a synced node on the public network. Each method answers a different question and none substitutes for another.

    Level Question Where
    Unit Does this method do what its contract says, with its callees faked? test/ in each library
    Component Do several units compose, such as connect with the interpreter unmocked? test/ in each library
    Protocol fixture Does a service dispatch each method and shape its response? libbitcoin-server/test/protocols/
    Acceptance Does a real client get the right answer from a live, synced node? libbitcoin-server/endpoints/
    Conformance Does each interface method match the protocol? the conformance record behind Conformance
    Sync Does the node validate the chain and how fast, from genesis, from public peers? Performance
    Coverage Which lines no test reaches? CI and local measurement

    Unit tests

    Every library has one Boost.Test binary under test/, mirroring the src/ and include/ tree one test file per source file.

    Library Cases
    system 6,411
    database 1,104
    network 1,600
    server 1,176
    node 115

    Unit tests are built and run in release configuration, since that is what ships, and are run on every push across every compiler and platform in the CI matrix. Debug builds are used only to debug.

    A test is one method under one condition with one expected result, and its name says so: subject__method__condition__result, with the result being the error code where one applies.

    BOOST_AUTO_TEST_CASE(block__constructor__data__expected)
BOOST_AUTO_TEST_CASE(hashmap__slab_construct__non_empty__expected_enabled)

    Style rules. No loops and no conditions in a test body or a fixture. A small range is written out as explicit assertions with numbered locals. Every assertion stays on one line however long, with nested expressions hoisted into named locals rather than wrapped. Comment almost nothing, since the name and the code are the documentation. Helpers are static free functions. Vocabulary is libbitcoin's, not bitcoind's.

    Property tests and reference tests, both. A round-trip test, serialize then deserialize, proves consistency. A property test, member matches and non-member does not, proves shape. Neither proves correctness, since both pass against an implementation that is consistently wrong. So every encoding and every consensus rule also has a reference test pinning exact published bytes: BIP test vectors for scripts, transactions, witnesses, taproot, addresses, keys, mnemonics and descriptors, NIST vectors for the hash functions, and libbitcoin's own vectors captured from the chain. The system tests reference the relevant BIP by number at each such assertion, which is how a reader finds the source of the expected value.

    Unit coverage independent of component coverage. A unit test fakes what the method calls, so that its lines are covered by its own tests and not incidentally by a component test above it. Mock seams are explicit: the machine tests use an accessor exposing the interpreter's protected surface, the database tests substitute an in-memory storage for the memory map so no files are touched, the network tests use mock sockets, acceptors, connectors and channels with scripted success and failure, and the node tests mock the network and query.

    Unreachable guards become assertions, not exclusions. A branch that cannot be reached is converted to BC_ASSERT rather than excluded from coverage, since excluding it would hide a defect if it ever became reachable.

    Protocol fixtures

    Each server interface has a fixture under test/protocols/<interface>/ that constructs a server_node over a small mocked store and attaches the service's session, so a test can send a request through the real dispatch path and assert on the response object. These tests prove that every declared method dispatches, parses its parameters, and serializes its result. They run in the unit test binary and need no network.

    Acceptance

    libbitcoin-server/endpoints/ is a pytest suite of real clients against a live node over real sockets: requests for HTTP, websocket-client for WebSocket, raw sockets for Electrum, and a standard-library WebSocket client for btcd. One file per interface, plus a transports file that exercises the same methods over TCP, HTTP and WebSocket to prove the transport does not change the answer.

    The node under test is synced against the public network to at least height 500,000 so that every test applies, including witness cases from height 481,824. Expected values are reference blocks and transactions from the chain, so a wrong answer is a wrong answer, not a disagreement with a mock.

    An interface is not done until it has its file here. The fixture proves dispatch and shape. The acceptance suite proves the answer.

    Conformance

    For the bitcoind, btcd, Electrum and Esplora interfaces, conformance is to the protocol, and the conformance record marks each method Full, Partial, Pending, WIP, Rejected or Scope with a note. Full means the method behaves as the protocol specifies on the same input, including error codes and the JSON types of every field. Number serialization form is not a difference. Value and type are. Rejected methods carry the reason, which is usually a privacy leak or a mining or wallet responsibility the node does not take on. The record is the single source for the landing page and for the Conformance and Interfaces sections.

    Sync

    A full synchronization from genesis against public peers is the end-to-end test of the node: every block validated, every rule exercised in chain context, every peer protocol driven by real peers. It is also the benchmark. Performance states the method: work measured in transactions not blocks, runs normalized to height 950,000, a cold start from reboot, a pinned source state recorded with every run, and run artifacts archived before the next run overwrites them. A run from an uncommitted tree supports no conclusion.

    Milestone sync tests the pipeline without script evaluation. Full validation tests everything. A run that stops at a configured height with maximum_height tests a bounded portion, and a store snapshot taken at that height is the starting point for the next.

    Coverage

    CI builds one leg with GCC in debug configuration and --coverage, runs the tests, and uploads line coverage to Coveralls, excluding the test tree, the examples, the bundled QR encoder and the mnemonic word catalogs. The exclusions are declared once in libbitcoin-build and generated into every repository's workflow.

    Locally on Windows the same measurement comes from the code coverage console shipped with Visual Studio, instrumenting the debug test binary through its PDB. Two rules make the numbers honest. Measure the debug build, since optimization reattributes lines to call sites and folds others away. And take the maximum over instantiations per source line, since a template line appears once per instantiation and is covered if any of them ran. Coverage is a map of what no test reaches, and the test written to reach a line must still assert a reference value, or it merely records what the code does.

    Continuous integration

    Every push to every repository builds and tests the GNU Autotools, CMake and CMake presets paths on Ubuntu with GCC 12 through 16 and Clang 18 and 19, macOS with Apple Clang, and Windows with Visual Studio 2026, in debug and release and static and dynamic linkage. The workflows are generated from libbitcoin-build, so the matrix is the same shape in every repository and a change to it lands everywhere at once. The install scripts run the server's tests at the end of every scripted build unless told not to.
