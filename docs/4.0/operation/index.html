    Operation

    bs is one executable with one optional configuration file. Started with no command it runs the node. Started with a command it performs that command and exits.

    Starting

    bs --config bs.cfg

    The configuration file path comes from --config, or from the BS_CONFIG environment variable, and is optional. Startup proceeds in a fixed order:

    1. Logging opens in the configured log directory, or on the console alone if none is set.
    2. Store. If the store directory exists it is opened. If open finds a flush lock, the previous run did not close cleanly, and the store is restored from its most recent snapshot before continuing. If the directory does not exist the store is created and the genesis block stored, so a first run needs no separate step.
    3. Reports. Body sizes, record counts, bucket counts, versions, log configuration and hardware support are written to the log.
    4. Warnings. Hardware below the compiled instruction set, memory below 8 GiB, 16 GiB or 32 GiB, disk space below 1 TiB, or a store not on an internal solid state drive each produce a warning. On a console the node then waits for Enter to continue or c to stop. --accept continues without asking.
    5. Milestone. On a fresh store without a configured milestone, the node shows the build's default milestone and asks whether to accept it as a block you have validated, or stop and set your own. Set bitcoin.milestone to the genesis hash at height zero to validate from genesis.
    6. Node. The network starts and seeds, the node runs, and the log reports that the node is started and then running.

    The node runs until it is stopped. Ctrl-C, SIGINT, SIGTERM or SIGHUP, the console c command, or a service manager stop all take the same path: the network closes, the store flushes and closes, the flush lock clears, and the log ends with a shutdown line. Closing typically takes well under two minutes. On a console the process then waits for Enter before exiting.

    Commands

    Command Effect
    --help, -h Print the command line options.
    --version, -v Print the versions of the five libraries and the compiled and stored schema versions.
    --hardware, -w Print which instruction sets the build was compiled for and which the machine supports, and any GPU.
    --settings, -s Print every setting with its effective value, marking those set in configuration.
    --newstore, -n Create the store in the configured directory and store the genesis block.
    --backup, -b Snapshot the store. Works on a store that another process has open.
    --restore, -r Restore the store from its most recent snapshot.
    --daemon [true\|false], -d Install or uninstall the node as a system service. See below.
    --user <credential>, -u The logon account for the installed service. Default is the system account.
    --information, -i Print store sizes, records, buckets, collision rates and chain progress.
    --flags, -f Walk the candidate chain and print every consensus rule transition.
    --buckets, -k Print hash table bucket densities.
    --collisions, -l Print hash table collision distributions. Allocates heavily and may be killed on a small machine.
    --get <hash>, -g Run the built-in read test.
    --put <hash>, -p Run the built-in write test.
    --accept, -a Answer every startup prompt with its default.

    Console

    While the node runs, single characters typed on the console are commands. Enter shows nothing, since echo is off.

    Key Action
    c Close the node. Same as Ctrl-C.
    b Back up the store to a snapshot while running. The network is suspended for the duration and resumed after.
    h Hold, suspending all peer connections.
    g Go, resuming peer connections. Refused while the disk is full or the store is faulted.
    z Zeroize a disk full condition after freeing space: reload the store and resume.
    e Report store error conditions per table, and the bytes to free if the disk is full.
    i Print store configuration, body sizes, records, buckets and collision rates.
    w Request a work distribution report from every peer channel.
    t Run the built-in test case.
    m Print this menu.

    Ten more keys toggle log levels for the running process: a application, n news, s session, p protocol, x proxy, r remote, f fault, q quitting, o objects, v verbose. A level not compiled into the build says so.

    Logs

    Two files rotate in the log directory. bs_end.log is the current file and bs_begin.log the previous one. When the current file reaches half of log.maximum_size it becomes the previous file and a new current file starts, so the pair together never exceeds the configured size and the startup banner is gone after two rotations. Each line is a UTC timestamp, a level letter and the message. The same lines go to the console.

    events.log in the same directory is not rotated. Each line is an event name, a value and the seconds since start. The events are the pipeline counters: header and block archived, validated, confirmed, organized and reorganized, bypass counts, transaction events, and timings for snapshot, prune, reload, filters and signature batches.

    Both streams are also available live over the admin service.

    Running as a service

    bs --daemon installs the node under the platform's service manager. bs --daemon false uninstalls it. Both need elevation. Starting and stopping the installed service is done with the platform's own tools. The service is installed to start automatically, with the configuration file and log directory given at install time.

    • Linux. A systemd unit at /etc/systemd/system/bs.service, type notify, wanting network-online.target, with a ten minute stop timeout. The node reports ready when running and extends the timeout while starting and stopping, so systemd never kills it mid-flush. Restart is deliberately not set.
    • Windows. A service named bs, display name Libbitcoin Server, delayed automatic start, with a ten minute pre-shutdown allowance. A non-system logon account is granted the service logon right at install.
    • macOS. A launchd daemon org.libbitcoin.bs under /Library/LaunchDaemons, run at load, output to console.log in the log directory. launchd clamps the exit timeout to sixty seconds and offers no readiness protocol.

    When a Windows desktop session ends, the node blocks shutdown while it flushes, showing "Flushing tables..." as the reason.

    Store lifecycle

    Snapshots. A snapshot copies the table heads into primary/, rotating the previous copy to secondary/, in a sequence of atomic renames. Take one from the console with b, or from a second process with bs --backup, at any time. Nothing else in the node schedules a snapshot, so a store that has never been snapshotted has no recovery path.

    Unclean shutdown. Killing the process, or losing power, leaves the flush lock in place. The next start detects it and restores from primary/, or secondary/ if primary/ is incomplete, truncating the bodies to the sizes the restored heads record. Sync resumes from there. With no snapshot the store is recreated empty. Never delete the flush lock by hand. It is the only signal that the store is inconsistent.

    Disk full is not a fault. The node logs the bytes required, suspends the network, fails the pending write, and checks free space every second. When space appears it reloads the store and resumes on its own. z on the console does the same on demand, and e shows how much to free.

    Faults are unrecoverable store errors. The node logs the fault, suspends the network, and keeps running so the operator can inspect it with e. Snapshot and reload are refused on a faulted store. Close it and restore.

    Stop height. With node.maximum_height set, the node stops requesting and validating blocks above that height and reports itself current. It does not exit. Close it as usual.

    Memory and disk

    The warning thresholds at startup state the requirements: 8 GiB of memory to run, 16 GiB for full validation, 32 GiB recommended, and 1 TiB of free disk for an unpruned mainnet store, on an internal solid state drive. The store's hash table heads are sized to the machine's RAM at creation and cannot be resized after, so create the store on the machine that will run it.
