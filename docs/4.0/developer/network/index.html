    network

    libbitcoin-network depends on system only. It provides the asynchronous connection layer described under Network layer and Concurrency. This page is about extending it.

    net

    network::net(const configuration& config, const logger& log,
    uint64_t required_services, uint64_t provided_services);

    start seeds and returns through its handler. run starts the inbound and outbound sessions. close blocks until the pool has joined and must not be called from a pool thread. suspend and resume stop and restart peer connections. network_settings(), service() and strand() expose the settings, the ASIO context and the strand. The thread safety contract is stated on the class: attach must be called on the network strand, and close must not be called concurrently.

    Logger

    network::logger is the log sink for the whole stack. write(level) returns a writer, a stream that commits its line when destroyed. fire(event, value) and span(event, start) record events and durations. subscribe_messages and subscribe_events receive them, which is how the executor writes files and the admin service streams. The LOGA, LOGN, LOGS, LOGP, LOGX, LOGF, LOGV and related macros write at a level and compile out when that level is not built.

    Writing a protocol

    A protocol implements one message exchange. Derive from protocol_peer for the peer network, or from the server's HTTP and RPC protocol bases for a service.

    class protocol_ping_106
  : public protocol_peer, protected tracker<protocol_ping_106>
{
public:
    typedef std::shared_ptr<protocol_ping_106> ptr;

    protocol_ping_106(const session::ptr& session,
        const channel::ptr& channel) NOEXCEPT;

    void start() NOEXCEPT override;
    void stopping(const code& ec) NOEXCEPT override;

protected:
    virtual void send_ping() NOEXCEPT;
    virtual void handle_timer(const code& ec) NOEXCEPT;
    virtual void handle_send_ping(const code& ec) NOEXCEPT;
    virtual bool handle_receive_ping(const code& ec,
        const messages::peer::ping::cptr& message) NOEXCEPT;
};

    start runs on the channel strand and is where the protocol subscribes to the messages it handles with SUBSCRIBE_CHANNEL(message, handler, ...). A handler receives the code and the message and returns whether to stay subscribed. SEND(message, handler, ...) sends a message and invokes the handler on completion. SUBSCRIBE_BROADCAST and BROADCAST reach every channel's protocol of the same type, which is how a new block is announced to all peers. stopping is the place to cancel timers. A protocol can stop its channel with stop(code) but never the session or the network, and start has no failure condition.

    Name a peer protocol by the protocol level that introduced its behavior, and attach it in the session according to what the peer negotiated.

    Writing a session

    A session maintains a set of channels and supplies three things: how to make a channel from a socket, what to attach for the handshake, and what to attach afterward.

    virtual channel::ptr create_channel(const socket::ptr& socket) NOEXCEPT = 0;
virtual void attach_handshake(const channel::ptr& channel,
    result_handler&& handler) NOEXCEPT = 0;
virtual void attach_protocols(const channel::ptr& channel) NOEXCEPT = 0;

    start_channel runs the sequence: create, attach handshake, on success attach protocols, and subscribe to the channel's stop so the session can release it. The base provides connectors, acceptors, the stop subscription and the defer helper for retry timers. The four peer sessions and the server's session_server are the models to copy.

    Messages

    A peer message is a struct with a cptr alias, its identifier, command string, version bounds, size(version), static deserialize and member serialize, and its fields. The message set is declared once, in interface::peer_dispatch, as a tuple of method<"command", message::cptr> entries, and messages::peer::registry derives the serializer and deserializer tables from it at compile time. Adding a message means adding the struct and one line to the tuple.

    The method template is shared with the server's RPC interfaces:

    template <text_t Text, typename ...Args>
struct method;

    Text is the wire name, Args the parameter types with optionals last, and the constructor takes the parameter names. A notifier always injects the code as the first handler argument, so a handler for a two-parameter method takes four arguments: the code, the method tag, and the two parameters.

    Settings

    network::settings holds the peer settings, outbound, inbound and manual, the feature flags, the address pool path, and the server settings structs that client-facing services parameterize: tcp_server, secure_server, tls_server, zmtp_server, http_server and websocket_server. Each service session takes one of these as its options_t. network::configuration wraps a settings with the chain selection.
