    database

    libbitcoin-database depends on system only. It provides the store and the query interface. The Store architecture page describes the tables and their layout. This page is about using them.

    Store and query

    The store is a template over its storage type, and the query is a template over the store.

    database::settings configuration{};
configuration.path = "bitcoin";

database::store<database::mmap> store{ configuration };
database::query<database::store<database::mmap>> query{ store };

if (store.create(handler)) { /* error */ }
if (!query.initialize(genesis_block)) { /* error */ }
// ...
store.close(handler);

    database::mmap is the production storage. The template parameter exists so tests can substitute an in-memory storage. The node fixes both types with the aliases node::store and node::query.

    store lifecycle methods each take an event_handler called with an event and a table as work proceeds, and return a code: create from nothing, open an existing store, snapshot and prune while open, restore from snapshot while closed, reload after disk full, close. report invokes an error_handler for every table in an error or full condition. A store that is open and loaded has taken the flush and process locks. get_transactor() returns a shared lock that a query holder takes for the duration of an operation.

    query is constructed over a store and is the only interface the node and server use. Its methods return bool or a value with a bool out parameter, never throw, and are thread safe against one another and against writes. It exposes the store's condition through get_fault(), is_fault(), is_full() and is_coalesced().

    Settings

    database::settings has path, the store directory, and one nested settings struct per table: simple_table for a body allocation and growth rate, bucket_table adding a bucket count, and hash_table adding an expected element count from which buckets are derived when not set. initialize(const system::settings&, bool limited) derives the defaults from the chain parameters and installed memory. Table sizing is fixed at creation and recorded in the store's envelope.

    Query surface

    The class is large and organized in layers, each in its own implementation file under impl/query:

    • Initialization. initialize(genesis) stores the genesis block as the first candidate and confirmed block.
    • Translation. From natural keys to links and between links: to_header(hash), to_tx(hash), to_block(tx_link), to_spenders(output), to_block_txs(link) and so on. A link is the unit of identity within the store, and queries that will be followed by other queries should carry links, not hashes.
    • Archive reads. get_header, get_block, get_transaction, sizes, heights, values, fees, and the get_wire_* variants that serialize directly to a sink without constructing the object.
    • Archive writes. set(header), set(transaction), set(block) and set_txs for headers-first association, each with the context needed to store the record.
    • Validation and confirmation. Chain state at a header, validation state get and set, block_confirmable, and the height indexation that maintains the candidate and confirmed chains.
    • Address, filter and unspent. The queries behind the address interfaces, BIP-158 filters, and the unspent set totals and MuHash commitment.

    Two rules from the primitives apply to anything built on the query. An accessor returned into a table body holds a shared remap lock, so use it for serialization and dispose of it immediately. Never hold an accessor into one table while reading the same table or another, or a remap waiting on your accessor while you wait on the table deadlocks. The query methods themselves respect this, so the rule bites only code that reaches below them.

    Errors

    database::code is std::error_code in the database category. The enumeration distinguishes store lifecycle errors, such as flush_lock, integrity, disk_full and mmap_failure, from table conditions. Disk full is reported as a condition, not a fault.
