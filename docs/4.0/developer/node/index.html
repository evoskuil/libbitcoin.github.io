    node

    libbitcoin-node depends on database and network. It provides full_node, described under Node pipeline. This page is about embedding and extending it.

    Embedding

    node::configuration config(chain::selection::mainnet);
// populate config.bitcoin, config.database, config.network, config.node
config.initialize();

node::store store(config.database);
node::query query(store);
store.open(handler);

network::logger log;
auto node = std::make_shared<node::full_node>(query, config, log);
node->start([&](const code& ec) { node->run(handler); });
// ...
node->close();
store.close(handler);

    node::configuration composes system::settings bitcoin, database::settings database, network::settings network and node::settings node, and initialize() reads files and derives dependent settings after parsing. node::store and node::query are the aliases database::store<database::mmap> and database::query<node::store>. The node takes the query by reference and does not own the store, so the store outlives the node and is closed after it.

    full_node is a network::net, so start, run, close, suspend and resume are the network's. It adds:

    • organize(header, handler) and organize(block, handler) to submit a header or block, as the peer protocols do.
    • prioritize(hash, handler), bitcoind's preciousblock.
    • submit(transactions, test, handler) to submit a package to the pool, validated only when test is set.
    • get_hashes and put_hashes, the download work interface used by the block protocols.
    • snapshot, prune and reload, each suspending the network and taking a store event handler.
    • fault(code), which suspends the network and leaves the node running.
    • archive() for the query, and accessors for each settings group.

    Chase events

    Everything in the node coordinates through chase events. The API is on full_node:

    object_key subscribe_chase(event_notifier&& handler) NOEXCEPT;
void subscribe_chase(event_notifier&& handler, event_completer&& complete) NOEXCEPT;
void unsubscribe_chase(object_key key) NOEXCEPT;
void notify(const code& ec, event_value value) NOEXCEPT;
void notify_one(object_key key, const code& ec, event_value value) NOEXCEPT;

    The first subscribe_chase is for chasers and requires the node strand. The second is for protocols and completes asynchronously. An event_value is a variant of the event payloads, and to_chase(value) and to_payload<chase::x>(value) extract the event and its payload. A handler returns whether to remain subscribed. The chase enumeration documents each event's issuer and handlers, and the payload aliases height_t, header_t, object_t, count_t and transaction_t give the payload types.

    Writing a chaser

    A chaser owns one stage of chain construction on its own strand.

    class chaser_example
  : public chaser
{
public:
    chaser_example(full_node& node) NOEXCEPT;
    code start() NOEXCEPT override;
    void stopping(const code& ec) NOEXCEPT override;

protected:
    virtual bool handle_chase(const code& ec, event_value value) NOEXCEPT;
    virtual void do_something(height_t height) NOEXCEPT;
};

    start is called on the node strand and is where the chaser calls subscribe_chase(BIND(handle_chase, _1, _2)) and initializes its position from the store. handle_chase runs on the notifier's strand, so it switches on to_chase(value), posts to its own strand with POST(do_something, payload), and returns. The do_ methods assert stranded() and do the work, reading and writing through archive(). To signal the rest of the pipeline, notify(error::success, chases::x{ payload }). stopping is non-blocking and stop blocks. The base provides closed(), suspended(), fault(code), resume(), and the settings accessors. Unlike a protocol, a chaser may fault the node.

    full_node constructs the ten chasers as members and starts them in do_start, so adding one means adding a member and a start call. The node protocols extend network::protocol_peer and subscribe to chase events through the protocol overload, which is how block announcements and downloads are driven from the pipeline.

    Errors

    node::code is std::error_code in the node category. Its enumeration covers store lifecycle transitions such as store_snapshot and store_prune, channel dispositions such as slow_channel, stalled_channel and sacrificed_channel, and organization results such as orphan_header and duplicate_block.
