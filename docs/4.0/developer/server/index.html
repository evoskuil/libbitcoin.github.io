    server

    libbitcoin-server depends on node. It provides server_node, the settings parser, the service sessions, the interface declarations and the bs console. This page is about adding a service or a method.

    server_node and configuration

    server_node derives from full_node and overrides run to start the ten service sessions after the network is running. server::configuration derives from node::configuration and adds the command line state, log::settings and server::settings, which holds one settings struct per service.

    server::parser derives from system::config::parser and loads four sources: command line options, positional arguments, environment variables with the BS_ prefix, and the configuration file, into parser::configured. It is constructed with the chain selection and the embedded pages of the native and admin services.

    Service sessions

    A service is a session_server parameterized by its protocols:

    template <typename ...Protocols>
class session_server
  : public server::session, public network::session_server

    The first protocol supplies options_t, the settings struct the session binds with, and channel_t, the channel type it constructs. Every protocol in the list is constructed and attached to each accepted channel in order. The existing services are aliases of this template:

    using session_admin = session_server<protocol_admin>;
using session_native = session_server<protocol_native>;
using session_esplora = session_server<protocol_esplora>;
using session_bitcoind = session_server<protocol_bitcoind_rest,
    protocol_bitcoind_blockchain, protocol_bitcoind_control,
    protocol_bitcoind_mining, protocol_bitcoind_network,
    protocol_bitcoind_notifications, protocol_bitcoind_test,
    protocol_bitcoind_transaction, protocol_bitcoind_utility,
    protocol_bitcoind_wallet, protocol_bitcoind>;
using session_electrum = session_handshake<protocol_electrum_version, protocol_electrum>;

    protocol_bitcoind is the terminal responder for unknown methods and must be attached last. Electrum and Sparrow use session_handshake, which runs a version negotiation protocol before attaching the rest. A new service is a new alias, a new settings struct in server::settings, its options in the parser, and an attach_ and start_ pair in server_node.

    Interfaces

    An interface declares its methods once, as a tuple of method entries, and everything else derives from that: parameter parsing, dispatch, the typed handler signatures, and the documentation on this site.

    struct electrum_methods
{
    static constexpr std::tuple methods
    {
        method<"blockchain.block.header", number_t, optional<0.0>>{ "height", "cp_height" },
        method<"blockchain.transaction.get", string_t, optional<false>>{ "tx_hash", "verbose" },
        // ...
    };

    template <size_t Index> using at = method_at<methods, Index>;
    using blockchain_block_header = at<3>;
    // ...
};

    Parameter types are string_t, number_t, boolean_t, value_t, object_t and array_t, with optional<default> for trailing optionals. A method declared with unimplemented is dispatchable but answered as not implemented, which keeps the interface complete while a method is pending.

    Dispatch

    protocol_rpc<Interface> is the base for a JSON-RPC service protocol. Its start registers the interface's method names and subscribes to HTTP posts and unknown requests, and its handlers validate host and origin, check whether the method belongs to this protocol, check the credential's permission for it, and dispatch to the subscribed handler with parsed and typed arguments.

    class protocol_electrum
  : public protocol_rpc<interface::electrum>
{
    using channel_t = channel_electrum;
    using options_t = channel_t::options_t;

    void start() NOEXCEPT override;

protected:
    void handle_blockchain_block_header(const code& ec,
        rpc_interface::blockchain_block_header, double height,
        double cp_height) NOEXCEPT;
};

void protocol_electrum::start() NOEXCEPT
{
    SUBSCRIBE_RPC(handle_blockchain_block_header, _1, _2, _3, _4);
    protocol_rpc::start();
}

    The handler takes the code, the method tag type, and one argument per declared parameter, so the placeholder count is two plus the parameter count. Responses go through send_result, send_error, send_code and send_notification, which forward to the channel, so the same handler serves the method over raw TCP by downgrade, HTTP, and WebSocket by upgrade. A method that does not belong to any attached protocol reaches handle_unclaimed.

    The bitcoind subgroups use protocol_bitcoind_dispatch<Interface> in the same way, and each subgroup is explicitly instantiated in its own translation unit so the dispatch metaprogramming compiles once.

    Adding a method

    1. Add the method<...> entry to the interface tuple and its using alias.
    2. Declare the handler on the protocol with the code, the tag type and the typed parameters.
    3. Subscribe it in start with SUBSCRIBE_RPC.
    4. Implement it against archive(), and answer with one of the senders.
    5. Add its row to the conformance record, which regenerates the Interfaces and Conformance pages, and its acceptance test to the endpoint suite.
