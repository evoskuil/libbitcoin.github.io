    Node pipeline

    full_node composes ten chasers. A chaser owns one stage of chain construction, runs on its own strand, and communicates with the other chasers only through chase events on the node's shared notifier. Chasers impose order where order is required and nowhere else. Unlike protocols, a chaser can stop the node.

    Chaser Owns
    header Chases stronger header branches for the candidate chain. Weak branches are retained in a hash table if not stored. A strong branch reorganizes the candidate chain and fires headers.
    block The blocks-first counterpart to header, organizing whole blocks and firing blocks.
    check Maintains the set of pending download identifiers for the candidate header chain and hands them to peers.
    validate Chases blocks in the candidate header chain for validation, on its own thread pool.
    confirm Chases valid blocks for confirmation and maintains the confirmed chain index.
    transaction Chases unconfirmed transactions: validates submitted packages and maintains the pool.
    template Constructs template blocks upon modification of the transaction DAG.
    estimate Maintains a running fee estimate cache over confirmed blocks.
    snapshot Prunes the prevout cache once the chain has coalesced, and takes a snapshot on snap.
    storage Monitors capacity following a disk full condition and restarts the network when space returns.

    header and block are two instantiations of one organize template. Which one starts is decided by the headers_first setting. The rest of the pipeline is the same in both modes.

    organize is the header chaser or the block chaser. block_in is the download protocol on each peer channel. out protocols are the header, block and transaction announcers and the fee estimator. Solid arrows are forward progress. Dashed arrows are failures, and every failure routes to organize, which is the only chaser that changes the candidate chain.

    Organize

    A header or block arrives from a peer protocol and is posted to the organize chaser. The sequence for each:

    1. Skip existing and orphan. A duplicate returns its stored state. A header whose parent is unknown is an orphan and is dropped.
    2. Validate the parent and obtain chain state. A parent already marked unconfirmable short-circuits, so a failed block cannot be looped over. A fork at or under the top reached checkpoint is rejected as a checkpoint conflict. Parent state comes from the cached top state, the header tree, or the store, in that order.
    3. Roll chain state forward from the archived parent to the new header, giving the context in which the header is checked and accepted.
    4. Validate and check currency. Header check and accept are never bypassed. Block bodies are validated later by the validate chaser, so malleation is ignored until then.
    5. Compute relative work. A header extending a weak branch is cached in the header tree and nothing else happens. Weak branches are held until the branch is strong enough to matter.
    6. Reorganize the candidate chain when the branch is stronger. The candidate chain is popped down to the branch point, the tree headers of the strong branch are archived and pushed, and the new header becomes the candidate top. The milestone flag is computed from the tree here because it trickles down, and is archived in the header record.
    7. Reset top state and notify. headers or blocks fires from the branch point once the chain is current, delayed at startup so headers can get current before block downloads start. regressed fires when the reorganization branched below the previous top. The top reached checkpoint advances and the tree is purged at and below it.

    Reorganization following an unconfirmable block, disorganize, walks the same path in reverse: the candidates above the invalid block are moved out of the index, the strongest known alternative branch is reevaluated, and disorganized fires so the downstream chasers reset.

    prioritize is bitcoind's preciousblock: a manual tie break between equal-work branches. Only the top of a cached branch can tie the candidate top. The preference is not retained.

    Check and download

    The check chaser tracks two frontiers over the candidate chain. requested is the last height in the current download window. advanced is requested less the blocks not yet validated. Peers do not decide what to download. A block_in protocol asks the chaser for a set of hashes with get_hashes, downloads them, and returns any it did not complete with put_hashes, otherwise the chain would remain gapped.

    The window is sized from the connection count. Each peer request is limited to the protocol's maximum inventory, and the window step is that maximum multiplied by the number of connections, capped by maximum_concurrency. Each block_in protocol reports its download speed to the chaser through the performer base. The chaser keeps the speeds of all channels and, once there are enough to measure, reports a channel whose speed falls below the others by more than allowed_deviation standard deviations. That channel splits its work, returning half its hashes for a faster peer, and stops. A stalled channel is dropped outright. stall splits every channel with work, and purge drops all outstanding work, both used when the window has to move.

    Each downloaded block is checked for identity before storage: the block hash, the merkle root, and the witness commitment. Under checkpoint or milestone that is all that is required, and a block failing it is stored as invalid so it is never downloaded again. Pruned nodes do not store input scripts or witnesses under bypass at all. Check, accept and connect are deferred to the validate chaser, because requiring only identity here permits the simplified block_view type. The protocol fires checked for each block and the chaser fires windowed when a full window completes.

    Validate

    The validate chaser walks the candidate chain by height from its last valid position. For each checked block it posts a validation job to its own pool with PARALLEL, so blocks validate concurrently up to the configured threads.

    A job populates the block's previous outputs from the store, then runs check, accept and connect in the block's chain context. Under milestone or checkpoint the script evaluation is bypassed and the block is marked valid on identity alone, which is the source of the milestone sync speed. Above the milestone everything runs.

    Signature verification is batched. Captured ECDSA and Schnorr signatures are written into the ecdsa and schnorr tables as rows, and the prevalid table carries each block's link set, so the batch is store-resident and crash-durable. Any completing pool thread may drain the batch. When a batch verifies, every block in it is marked valid at once and valid fires for each. A failure marks the block invalid and unvalid fires, routing to organize. Capturing is disabled once the confirmed chain is current and the node is not under bypass, so at the top of the chain signatures verify directly.

    Confirm

    The confirm chaser follows valid by height. A block becomes confirmable when every input spends an output that is strong at that height, with no double spend. The strong_tx index records which transactions are strong in which block, and it is what confirmation consults. A confirmable block is pushed to the confirmed index and organized fires with its link. When the block's branch replaces a previously confirmed one, the popped blocks are rolled back and reorganized fires for each. An unconfirmable block fires unconfirmable, routing to organize.

    Once the confirmed chain is current, each new confirmation also fires block, which the transaction and snapshot chasers act on, and starts a stale timer. If no block arrives within the timer, stale fires so the transaction protocols know the chain is no longer current.

    Snapshot, storage and the pool

    The snapshot chaser prunes the prevout cache once, on the first confirmed block after the candidate and confirmed chains have coalesced, since the cache exists to serve validation of blocks that are now behind the confirmed top. It also handles snap by taking a snapshot, though nothing in the node issues that event today, so snapshots are operator driven through the console. Snapshots and prunes suspend the network for their duration and resume it afterward.

    The storage chaser wakes on space, which the node fires when a disk full condition is detected, and polls the store's required space on a timer. When enough has been freed it reloads the store and fires unfull, which the validate chaser uses to resume.

    The transaction chaser accepts submitted packages as a whole. A package is validated in the current pool context and archived unless submitted as a test, in which case nothing is stored. Each organized or reorganized block recomputes the pool context, and if the chain is found to be no longer current the pool is closed until it is. transaction fires for each accepted transaction, and the template chaser rebuilds the block template on it. The estimate chaser populates a fee accumulator from confirmed blocks up to fee_estimate_horizon and resets if the chain falls far behind.
