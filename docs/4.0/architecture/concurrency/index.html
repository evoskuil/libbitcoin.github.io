    Concurrency

    The rule across the stack is that a thread never blocks waiting for another thread to release shared state. State has one owner, a strand, and is read or changed only by handlers running on that strand. Where a primitive does appear it guards a rare structural event, such as growing a file, and never a hot path.

    Node and server declare no mutex. Network declares one, in a diagnostics capture buffer. The store's few guard structural events described below. Strands, by contrast, are everywhere: stranded() asserts guard several hundred method entries across network, node and server.

    The proactor

    network::threadpool owns one boost::asio::io_context and a set of threads that run it. Every socket operation, timer and posted handler completes on one of those threads. Nothing blocks on I/O. A read is issued and the thread moves on. When bytes arrive, the completion handler is dispatched to whichever thread is free.

    Ordering comes from strands. A boost::asio::strand is an executor that guarantees its handlers never run concurrently, without pinning them to a thread. The pattern throughout the stack is: an object owns a strand, its mutable state is touched only from handlers on that strand, and any method callable from outside posts to the strand rather than acting directly. The POST macro does this for a member function, BIND produces the bound handler, and PARALLEL posts to the pool without a strand for work that is independent.

    Ownership by strand

    net has one strand for cross-object state: session attachment, suspend and resume, subscriptions. Its stranded() returns true only on that strand, and start, run and close assert it.

    Sockets post every handler except accept to an internal strand. Proxies and therefore channels run all completion and event handlers on the channel strand. A channel's protocols share that strand, so a protocol's handle_ methods are always stranded and a protocol never needs a lock of its own. A protocol is thread safe in the documented sense that its public methods either post to the strand or are called during handshake before concurrency exists.

    Sessions are thread safe by the same construction. Each maintains a channel set on the net strand.

    Chasers each own a strand on the network pool. A chaser's handle_chase runs on the strand of the notifier that fired it, so a chaser that needs its own state posts to itself with POST and returns. Chasers never call one another. The validate chaser additionally owns a second thread pool and strand, sized by the threads setting and scheduled at the configured priority, so block validation cannot starve network handling.

    Service sessions in the server derive from the same session and channel machinery and inherit its strands. The server adds no synchronization primitive.

    Lifetime without locks

    Handlers outlive the calls that create them, so object lifetime is managed by the handlers themselves. BIND_SHARED binds a member function to a shared_ptr obtained from shared_from_base, keeping the object alive until the handler runs. BIND_WEAK binds through a weak_ptr and the handler becomes a no-op if the object has gone. Channels warn that a pointer should only be retained while subscribed to the channel's stop, and released in the stop handler, otherwise the channel leaks.

    Stop is a message, not a lock. Every proxy, session and chaser exposes an idempotent stop that posts to its strand, and subscribers to stop are invoked there with error::service_stopped. net::close is the one blocking call in the stack. It is documented as not callable from a pool thread, because it joins the pool.

    Joining without locks

    Three families of handler combinators replace condition variables and barriers.

    Subscribers. subscriber, desubscriber and unsubscriber hold handlers in a queue or keyed map. All methods must be invoked on the owning strand and handlers are invoked there. notify invokes each in order, stop invokes each with a code and drops them. A desubscriber's handler returns whether to remain subscribed. The chase event bus, connect and close notification, and every channel's stop subscription are built on these.

    Races. A race joins N asynchronous completions into one. race_all completes on the last finisher. race_any completes on the first. race_speed<N> completes with the first result once all N have finished, and is what the validate chaser uses to complete a block with its first error. race_quality completes on the first success, used by outbound sessions to keep the first handshake that succeeds. race_unity completes on the first failure once all have finished, used by the seed session to continue once enough seeding has occurred. race_volume completes when a count is reached. All but race_any are documented not thread safe because they run on a strand.

    Turnstiles. The validate chaser batches signatures across blocks. Batch state lives in the store rather than in memory, in the ecdsa, schnorr and prevalid tables, so the batch is crash-durable and any completing pool thread can service it without coordination. The drain and commit exclusion is a turnstile: entering capture and exiting capture are counted so that a commit waits for in-flight captures to leave, without blocking any writer from entering.

    The store

    The store is fully concurrent for writers against writers and for readers against writers. Neither takes a lock on the request path. This rests on three facts: bodies are append only, an element becomes reachable only after it is complete, and the publication that makes it reachable is a single atomic word store with release semantics.

    Allocation. A writer claims rows by advancing the body's logical_ extent with a compare-and-swap. Two writers never receive the same rows, and neither waits for the other. The memory map maintains a chain of extents, settled_ <= frontier_ <= logical_ <= capacity_ <= file_, in which the lower bounds move on the lock-free fast path and the upper bounds move only under the remap lock, so a stale-low read of a lower bound can never falsify the chain.

    Publication. A hash table head is a memory-mapped array of bucket cells. A cell holds the link of the newest element in the bucket in its low bits and a small bloom filter over the keys in that bucket in the rest. Its width is set per table by the schema. To commit an element, the writer writes the element's body and its next link, which is the bucket's current top, then issues a release fence, then replaces the cell by compare-and-swap with the new link and the updated filter. The fence orders the element's bytes before the word that exposes them, so a reader that observes the new cell observes a complete element and a complete chain. Contention between two writers on one bucket costs one retry of the swap. A reader loads the cell with acquire semantics, screens the key against the filter, and walks the chain by following next links, none of which change once published. This is the path for a cell of native word width. A cell of another width cannot be swapped atomically, so that head falls back to a shared mutex, exclusive for the update and shared for the read. The positional height indexes store links with relaxed atomics, since their ordering comes from the reorganization interlock below.

    Remap. The one exclusive event is growing a body past its capacity, because it can move the mapping. An accessor into a body holds a shared remap lock for its lifetime and remap takes the exclusive lock. So the primitives insist that an iterator, reader or finalizer be used for serialization and disposed immediately, and that no accessor into one table be held while reading the same table or another. A remap waiting on that accessor while the accessor waits on a read of the same table is a deadlock. The hashmap.get(iterator, ...) overload exists so a read can complete through an accessor already held. Memory commitment follows use in chunks within a standing disk reservation, so growth is a syscall per chunk and not a remap.

    Interlocks. Two shared mutexes in query order candidate and confirmed reorganization against concurrent readers of those indexes. The store transactor is a shared lock taken by query holders for the duration of an operation, with snapshot, prune and close taking the exclusive side. Close waits in one-second attempts until readers have drained. These guard chain-level events measured in seconds, not element writes measured in nanoseconds.

    What this buys

    There is no lock ordering to reason about, because there are no nested locks in the request path. A slow peer cannot stall another, because their channels are on different strands and a proxy's write queue is per channel. A slow disk cannot stall the network, because validation runs on its own pool and the network pool's handlers are short. A crash cannot corrupt the store's in-flight state, because the state that matters, including the signature batch, is written through to the store as it is produced.
