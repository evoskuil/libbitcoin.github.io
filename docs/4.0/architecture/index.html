    Architecture

    bs is one process built from five libraries. Each library is its own repository and depends only on the libraries below it.

    flowchart TB
    server[libbitcoin-server]
    node[libbitcoin-node]
    network[libbitcoin-network]
    database[libbitcoin-database]
    system[libbitcoin-system]
    server --> node
    node --> network
    node --> database
    network --> system
    database --> system

    Libraries

    libbitcoin-system is the foundation. It holds the chain types (block, header, transaction, script, witness), the script machine and its interpreter, hashing (SHA family, RIPEMD, SHA-3, SipHash, MuHash) with hardware intrinsics for Intel, NEON and SVE, and the wallet primitives (keys, addresses, mnemonics, descriptors, PSBT). Serialization, streams, endianness, radix encodings, unicode and configuration parsing live here too. Nothing in system knows about a network or a disk.

    libbitcoin-database is the store. Tables are memory-mapped files built from three primitives: arraymap for positional records, hashmap for keyed records, and nomap for unkeyed bodies. The store owns the table set and the lifecycle operations create, open, snapshot, prune, restore, reload and close. The query class is the only interface the node and server use to read or write it.

    libbitcoin-network is the connection layer. net owns the thread pool and a single strand, and runs sessions. A session maintains a set of channels. A channel is a proxy with timers and connection state, and a proxy is a serialized message pump over a socket. protocol objects attach to a channel and implement one message exchange each. Peer protocols are versioned by the protocol level that introduced them, so protocol_ping_60001 and protocol_version_70016 name their own history. The same machinery carries HTTP, JSON-RPC, TLS and ZMTP for client-server work, and SOCKS5 and I2P SAM for anonymity transports.

    libbitcoin-node is the synchronizer. full_node derives from net, adds the store query, and composes ten chasers. Each chaser owns one stage of the pipeline and communicates with the others only through chase events. Node protocols extend the peer protocols with the block, header, transaction and filter exchanges that drive the chasers.

    libbitcoin-server is the service layer. server_node derives from full_node and adds one session per client-facing service: admin, native, bitcoind, btcd, electrum, sparrow, esplora, stratum_v1, stratum_v2 and bitcoind_zmq. Each service session is a session_server parameterized by its protocol stack, so connection management, binding, and black and white listing are shared while parsing and serialization are per interface. The console directory holds the bs executable itself.

    Process lifecycle

    The bs executable is the console executor. Its run sequence is fixed:

    flowchart LR
    A[open store] --> B[construct node] --> C[start] --> D[run] --> E[services] --> F[wait] --> G[close]

    Store. If the store path exists it is opened. A flush.lock left by an unclean shutdown makes open fail and triggers restore from the most recent snapshot. If the path does not exist the store is created. Only then is the node constructed over the store's query.

    Start. full_node::start starts every chaser, the header chaser or the block chaser according to headers_first, then check, validate, confirm, transaction, template, estimate, snapshot and storage. Control then passes to net::start, which starts the manual session, loads the hosts file, and runs the seed session to completion.

    Run. full_node::run fires the chase::start event, which tells the chasers to begin from their current store positions. net::run connects the configured manual peers, then starts the inbound session, then the outbound session. server_node::run follows with the ten service sessions in order.

    Stop. Close is idempotent and blocks until work has drained. The chasers are stopped, the event subscriber is stopped with chase::stop, the network closes its sessions and joins the thread pool, and finally the store is closed, which clears the flush lock.

    From the network layer up the stack runs on the ASIO proactor. State belongs to a strand and changes only in handlers posted to it, so threads never wait on one another. Node and server contain no mutex at all, and network contains one, in a diagnostics capture. The store uses atomics and compare-and-swap for its hot paths and reserves exclusive locking for remapping a grown file. Concurrency covers the design in full.

    Event flow

    Chasers do not call each other. Each subscribes to chase events and issues its own. The event names are the pipeline vocabulary:

    Stage Events issued Issued by
    Candidate chain headers, blocks, regressed, disorganized header, block, organize
    Download download, starved, split, stall, purge check, block_in protocol
    Check checked, unchecked, windowed block_in protocol, check
    Validate valid, unvalid validate
    Confirm confirmable, unconfirmable, organized, reorganized, block, stale confirm
    Mining transaction, template_ transaction, template
    Control start, bump, suspend, resume, space, unfull, snap, report, stop full_node, organize, storage, executor; snap has no issuer today

    Failures flow back to organize, which reorganizes the candidate chain away from the offending block and re-issues bump so the downstream chasers restart from their new positions.
