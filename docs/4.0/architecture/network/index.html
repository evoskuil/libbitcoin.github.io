    Network layer

    libbitcoin-network is a general asynchronous connection layer. The peer-to-peer protocol is one client of it. HTTP, JSON-RPC, WebSocket, TLS, ZMTP and the BIP-324 encrypted transport are the others, and every service the server exposes is built on the same session, channel and protocol classes as a peer connection.

    net

    net owns the threadpool, the strand on which cross-object state changes, and the hosts address pool. It runs sessions. start starts the manual session, loads the hosts file, and runs the seed session to completion. run connects the configured manual peers, then starts the inbound session, then the outbound session. close stops everything and joins the pool. suspend and resume stop and restart peer connections without touching service connections, which are managed independently.

    net also publishes two subscriptions: subscribe_connect, invoked for each channel created, and subscribe_close, invoked on service stop. Disconnection has no subscription of its own. A subscriber to connect subscribes to each channel's stop instead.

    Sessions

    A session maintains a set of channels and is thread safe by construction, since it works on the net strand. The four peer sessions differ in how they obtain connections:

    • manual maintains a connection to each configured peer, reconnecting on loss, with a callback per attempt.
    • seed connects to the configured seeds, collects addresses into the hosts pool, and completes once enough seeding has occurred, joined by a race_unity.
    • inbound accepts connections on the configured binds up to the inbound connection limit, subject to black and white lists and the loopback guard.
    • outbound takes random addresses from the hosts pool and races several connection attempts, keeping the first handshake that succeeds by race_quality.

    session_server is the client-server variant. It is documented as nearly identical to session_inbound, differing in handshake and protocol attachment, and it does not derive from session_peer so that downstream services do not inherit peer semantics.

    Channels, proxies and sockets

    A socket wraps an ASIO TCP socket, or one of its TLS, BIP-324 or ZMTP variants, and posts all handlers except accept to an internal strand.

    A proxy is a serialized message pump over a socket. It owns the read loop and a write queue. Full-duplex writes are queued to prevent interleaving, and the completion of one write starts the next. Sends are rate limited by allocating each bytes / rate_limit of time and deferring completion by whatever the write did not consume, which throttles the channel without a second queue. Reads are not metered, because they are bounded by protocol correctness. When a channel stops with pending writes the queue is purged and the purged handlers are not invoked.

    A channel is a proxy with timers and connection state: expiration, inactivity, creation and last activity times, a nonce for the loopback guard, and an identifier for session subscribers. Protocols are attached to a channel with attach<protocol>() and started by the caller, on the strand. A channel also holds the dispatch gate. A protocol that needs to defer the next read until its dispatch completes, such as a query that reads the store, holds the gate and releases it when done, and the read is re-armed on release.

    Connections are made by connector and acceptor, each with a variant: connector_socks for outbound through a SOCKS5 proxy such as Tor, and acceptor_sam for inbound forwarded by an I2P SAM bridge. Both are stranded and expose an idempotent thread safe stop.

    Protocols

    A protocol implements one message exchange and nothing else. It subscribes to the messages it handles, its handle_ methods run on the channel strand, and it can stop its channel but never its session or the network. Protocol start has no failure condition.

    Peer protocols are named by the protocol level that introduced their behavior, and the name is the history: protocol_version_106, protocol_version_70001, protocol_version_70002, protocol_version_70016; protocol_ping_106, protocol_ping_60001; protocol_address_in_209 and protocol_address_in_70016 with their _out counterparts; protocol_seed_209 and protocol_seed_70016; protocol_alert_311; protocol_reject_70002. The node adds the block, header, transaction and filter exchanges in the same style, from protocol_block_in_106 through protocol_transaction_in_70013 and protocol_filter_out_70015.

    Selection is two-staged. At handshake, session_peer attaches the highest version protocol the configured protocol_maximum allows: 70016 if BIP-155 is configured and enable_address_v2 is set, else 70002 if BIP-61 and enable_reject, else 70001 if BIP-37, else 106. After the handshake, protocols are attached according to what was negotiated with the peer: ping with nonce if BIP-31, the plain ping otherwise; address v2 if BIP-155, else the original address exchange; alert and reject only if negotiated and enabled. A declined protocol is handled by registering its negotiation message and subscribing nothing, so an unknown command is never silently ignored.

    Messages

    Peer messages live under messages/peer, one class per message with a common heading. Serialization goes through a registry so a channel deserializes only messages a protocol has subscribed to. HTTP requests and responses, JSON bodies, and RPC framing live beside them and are used by the server's service protocols.

    Transports

    • BIP-324 is the p2ps socket variant. The session cipher generates an ephemeral keypair, exchanges ElligatorSwift-encoded public keys in the clear, and derives the directional packet ciphers, garbage terminators and session identifier from the shared secret. Decoy packets are detected and dropped. It is selected per outbound address by the privacy flag.
    • TLS wraps a socket in an ASIO SSL context configured from tls_server settings: key, certificate, certificate authority, and passphrase.
    • ZMTP implements the CurveZMQ mechanism over ZMTP framing, with NaCl boxes for the handshake commands and messages, used by the bitcoind_zmq notification service.
    • HTTP and WebSocket are protocols, not sockets. protocol_http subscribes to requests by verb, dispatches to virtual methods, and answers disallowed verbs and invalid requests with standard responses. A WebSocket upgrade is accepted by the proxy on request.

    Hosts

    The hosts pool is a thread safe address table loaded from and saved to a line-oriented text file at the configured path. Duplicates and invalid addresses are discarded. Outbound sessions take one random connectable address of a requested family, and the pool reserves addresses currently connected so they are not taken twice. Counts by family are available for administration.
